# 捕鱼大世界抓包技术文档（Reflexion 复盘版）

> 用途：以后添加新功能需要逆向游戏协议时，按本文档流程抓包，避免重复踩坑。
> 本文档汇总 2026-08-10 与 2026-08-15 两次抓包的经验，含完整流程、错误复盘、协议要点与快速检查表。

## 1. 背景与目标环境

### 1.1 抓什么

- 目标游戏：捕鱼大世界 `com.shiyi.by3d`（Unity + il2cpp）
- 主游戏协议：`https://i.bydsj3d.com/BKBY3DHttpReq/HandleHttpReq.do`
  - POST body：`v=<UPPERHEX(payload)>`
  - payload：`u16 msgType + u16 version(33) + fields + ASCII_UPPERHEX(MD5(payload[:-32] + KEY))`
  - KEY = `qwerpoiuasdflkjh`（见 `scripts/bydsj_client.py`）
- 通行证登录（Gaia）：`https://dawn.shiyiyx.com`（手机号/账号密码登录、换取 LC_ token）
- token 登录：`i.bydsj3d.com/BKBY3DHttpReq/TokenLoginReq.do`（msgType 6674）
- 更新检查：`update.buyudashijie.com`（与游戏数据无关，一般不用抓）

### 1.2 环境

- 模拟器：LDPlayer9（Android 9，**已 root**），adb 路径 `E:\leidian\LDPlayer9\adb.exe`
- 抓包代理：mitmproxy（项目 `.venv` 内安装），用 `mitmweb` 可视化 / 落盘
- 证书：`dumps/20260810/mitmproxy/`（mitmproxy CA，**必须复用这把 CA**，见 3.2）
- 关键事实：游戏服务器 IP 会轮换（47.98.142.149、183.247.246.67、111.32.210.108、36.156.3.184、139.224.57.x 等），且游戏**不信任**系统代理设置，必须用透明重定向

## 2. 标准抓包流程

### 2.1 准备模拟器与证书

```powershell
# 1) 确认设备并获取 root
E:\leidian\LDPlayer9\adb.exe devices
E:\leidian\LDPlayer9\adb.exe -s emulator-5554 root

# 2) 准备系统证书库目录（完整拷贝一次，之后只改这一个目录）
#    先手动把 /system/etc/security/cacerts/ 里的 .0 文件全部拉到
#    /data/local/tmp/cacerts/（之前已做过，模拟器里目录仍在可复用）
```

计算 mitmproxy CA 的 Android 证书文件名（**字节序坑，见 3.1**）：

```python
from cryptography import x509
from cryptography.hazmat.primitives.serialization import Encoding
import asn1crypto.x509 as acx, hashlib, struct
der = x509.load_pem_x509_certificate(open('dumps/20260810/mitmproxy/mitmproxy-ca-cert.pem','rb').read()).public_bytes(Encoding.DER)
subject_der = acx.Certificate.load(der).subject.dump()
h = hashlib.md5(subject_der).digest()
print('%08x.0' % struct.unpack('<I', h[:4])[0])   # 本 CA 实测为 0d0f75c8.0
```

把 `mitmproxy-ca-cert.der`（825 字节，**DER 格式**）复制为 `/data/local/tmp/cacerts/<hash>.0`，
然后 bind mount 到系统证书库（/system 只读，不能直接写）：

```bash
adb shell "mount -o bind /data/local/tmp/cacerts /system/etc/security/cacerts"
adb shell "ls /system/etc/security/cacerts/0d0f75c8.0"   # 必须存在
```

> 若模拟器被重置：先 `mkdir -p /data/local/tmp/cacerts`，再 `cp /system/etc/security/cacerts/*.0 /data/local/tmp/cacerts/`（作为 root 可读），最后放入 mitm 证书并 bind mount。

### 2.2 路由：hosts 覆盖 + iptables + adb reverse

用 hosts 把游戏域名固定到本机回环，**彻底解决服务器 IP 轮换**（见 3.3）：

```bash
# /data/local/tmp/hosts_override 内容：
#   127.0.0.1       i.bydsj3d.com
#   127.0.0.2       dawn.shiyiyx.com
adb push dumps/20260815/hosts_override /data/local/tmp/hosts_override
adb shell "mount -o bind /data/local/tmp/hosts_override /system/etc/hosts"
adb shell "cat /system/etc/hosts"            # 验证
adb shell "ping -c1 i.bydsj3d.com"           # 应解析到 127.0.0.1
```

iptables 重定向（保活脚本见 `dumps/20260815/keep_dnat_loop.sh`）：

```bash
# 核心规则：回环 443 → 代理端口（通过 adb reverse 转发到宿主机）
iptables -t nat -A OUTPUT -p tcp -d 127.0.0.1 --dport 443 -j DNAT --to-destination 127.0.0.1:8080
iptables -t nat -A OUTPUT -p tcp -d 127.0.0.2 --dport 443 -j DNAT --to-destination 127.0.0.1:8081
# 兜底规则：已知游戏服务器 IP 直接转 8080（防止 hosts 不生效/游戏自带 DNS）
# 139.224.57.x（Gaia）转 8081
```

宿主机转发（Windows 侧）：

```powershell
E:\leidian\LDPlayer9\adb.exe reverse tcp:8080 tcp:8080
E:\leidian\LDPlayer9\adb.exe reverse tcp:8081 tcp:8081
```

### 2.3 启动代理（两个实例）

**必须复用旧 CA 目录 `dumps/20260810/mitmproxy`**，否则新生成的 CA 模拟器不信任（见 3.2）：

```powershell
# 主游戏协议 → 8080（web UI 用 8091，避开 8081）
.\.venv\Scripts\mitmweb.exe --listen-host 127.0.0.1 --listen-port 8080 `
  --mode "reverse:https://i.bydsj3d.com" --web-host 127.0.0.1 --web-port 8091 `
  --set web_open_browser=false --set ssl_insecure=true `
  --set confdir=dumps/20260810/mitmproxy -w dumps/20260815/capture_game.mitm

# Gaia 登录 → 8081（web UI 用 8092）
.\.venv\Scripts\mitmweb.exe --listen-host 127.0.0.1 --listen-port 8081 `
  --mode "reverse:https://dawn.shiyiyx.com" --web-host 127.0.0.1 --web-port 8092 `
  --set web_open_browser=false --set ssl_insecure=true `
  --set confdir=dumps/20260810/mitmproxy -w dumps/20260815/capture_gaia.mitm
```

> 不要用 `python -m mitmweb`（该入口不存在）；直接用 `.venv\Scripts\mitmweb.exe`。
> 默认 confdir 是 `%USERPROFILE%\.mitmproxy`，若被系统拒绝写入，就显式指定项目内目录。

### 2.4 端到端验证（必做，否则别让用户操作）

在模拟器里用 curl 走完整链路，必须看到 `HTTP:200 TLS:0`：

```bash
# 注意：--cacert 必须给 PEM（系统库里的 .0 是 DER，直接给会 TLS 校验失败）
adb push dumps/20260810/mitmproxy/mitmproxy-ca-cert.pem /data/local/tmp/ca.pem
adb shell "curl -s -m 15 --cacert /data/local/tmp/ca.pem -o /dev/null -w 'HTTP:%{http_code} TLS:%{ssl_verify_result}\n' https://i.bydsj3d.com/BKBY3DHttpReq/HandleHttpReq.do"
# 期望输出：HTTP:200 TLS:0
```

再解析一次 `.mitm` 文件确认流量落盘，然后才让用户在游戏里操作。

### 2.5 操作与确认

1. 一次只做一个功能，做完先停下解析，避免多个操作混在一起；
2. 用 `mitmproxy.io.FlowReader` 解析：按时间戳/msgType 筛出目标请求；
3. 封包格式用纯函数对拍抓包 hex（先离线，不碰网络）；
4. 用真实账号验证：登录 → 领前背包 → 操作 → 领后背包，对比数量变化；
5. 新结论登记到 `dumps/<日期>/抓包记录.md` 与本文档“已知 msgType”表。

### 2.6 清理

- 关闭 mitmweb（两个会话 Ctrl+C）；
- `adb shell "pkill -f keep_dnat_loop"`（先 `ps -A | grep keep_dnat` 拿 PID，避免 pkill 自匹配）；
- `adb shell "iptables -t nat -F OUTPUT"`；
- `adb shell "umount /system/etc/hosts; umount /system/etc/security/cacerts"`；
- `adb reverse --remove-all`。

模拟器重启后这些运行时配置（iptables/bind mount/adb reverse）本身就会消失。

## 3. 踩坑复盘（Reflexion）

### 3.1 证书文件名字节序（浪费了大量时间）

- 现象：`openssl x509 -subject_hash_old` 输出 `c8750f0d`，但项目里 `certname.txt` 记的是 `0d0f75c8`，文件也确实是 `0d0f75c8.0` 且**当时抓包成功**。
- 根因：Android/OpenSSL 的 `X509_NAME_hash_old` 把 MD5 前 4 字节按小端拼成 u32 再格式化（`0d0f75c8`），而部分工具按大端显示（`c8750f0d`）。
- 预防：**以实测为准**——把证书放进系统库后，在模拟器里跑一次 curl 验证（2.4）；不要凭单一工具输出取名。保险做法：两个文件名都放一份。

### 3.2 两把 CA 混用（confdir 生成新 CA）

- 现象：`curl --cacert 0d0f75c8.0` 一直 `TLS:1`；后来发现 mitmweb 用的是**另一把** CA。
- 根因：`dumps/20260810/mitm/` 与 `dumps/20260810/mitmproxy/` 两个目录各有一把 CA；首次启动用错目录，mitmweb 就用自己的新 CA 签发证书，模拟器只信任旧 CA。
- 预防：**启动前对比 CA 哈希**——用 cryptography 读 confdir 里 `mitmproxy-ca.pem` 的证书，与模拟器安装的 `.der` 比对 SHA-256；匹配再启动。

### 3.3 游戏服务器 IP 轮换，流量绕过 DNAT

- 现象：第一次登录时抓包文件里只有 curl 测试，游戏真实请求一条都没有；`netstat` 发现游戏连的是 36.156.3.184、139.224.57.6，都不在 DNAT 列表。
- 根因：DNAT 按 IP 白名单匹配，游戏 DNS 轮换/多出口 IP 随时会变。
- 预防：**hosts 覆盖是根治方案**——把 `i.bydsj3d.com` 钉到 127.0.0.1，无论 DNS 怎么变都进代理；IP 白名单规则只做兜底。

### 3.4 已建立的连接绕过 DNAT

- 现象：代理配好后，游戏“旧连接”仍直连服务器。
- 根因：iptables DNAT 只对**新建连接**生效，established 连接继续走原路径。
- 预防：改完路由后**彻底重启游戏/重新登录**，让所有连接重新建立。

### 3.5 “获取数据失败[4,9]”误判

- 现象：用户登录报错，怀疑是抓包导致。
- 排查：抓包文件里没有该请求 → 流量根本没进代理 → 是游戏服务器自身返回，与抓包无关（结合风控背景判断）。
- 教训：**先看抓包有没有记录，再下结论**；不要凭现象猜原因。抓包工具的价值就是提供证据。

### 3.6 风控限制

- 现象：同 IP 短时间登录多个账号触发“高风险的昵称登录,请稍后再试”；[4,9] 也可能与风控有关。
- 预防：抓包登录不要连续极速操作；批量验证时保持间隔（软件内默认 5-15 秒）；新功能验证用“未领取/未操作过”的账号。

### 3.7 端口冲突

- 现象：mitmweb 的 web UI 默认 8081，与第二个代理监听端口撞车。
- 预防：主代理 8080 → web 8091；Gaia 代理 8081 → web 8092；启动前 `netstat -ano | findstr ":8080 :8081"` 查占用。

### 3.8 keep_dnat_loop 残留进程

- 现象：清掉规则后 3 秒又出现 8081 旧规则。
- 根因：旧保活脚本进程还在跑，周期性重新添加旧规则。
- 预防：先 `ps -A | grep keep_dnat` 拿到 PID 逐个 kill，再 flush 规则，再启动新脚本；改脚本后 push 覆盖再重启。

### 3.9 pkill 自匹配杀死 shell

- 现象：`adb shell "pkill -f keep_dnat; ..."` 命令中途退出。
- 根因：pkill -f 匹配到了命令行自身包含的关键字。
- 预防：先 pgrep/ps 拿 PID 再 kill；或把关键字拆开避免自匹配。

### 3.10 Windows 写权限（沙箱/AppData）

- 现象：mitmproxy 默认 confdir `%USERPROFILE%\.mitmproxy` 报 `PermissionError`；Nuitka 缓存目录同理。
- 预防：抓包/打包都显式把缓存目录指到项目内（如 `--set confdir=dumps/...`、`NUITKA_CACHE_DIR=项目/.nuitka_cache`）。

### 3.11 curl --cacert 需要 PEM

- 现象：模拟器 curl 用系统库 `.0`（DER）文件做 `--cacert` 一直 TLS:1。
- 根因：curl 的 `--cacert` 只认 PEM；系统证书库是 DER。
- 预防：验证链路时把 `mitmproxy-ca-cert.pem` push 到 `/data/local/tmp/ca.pem` 再传 `--cacert`。游戏本身走系统证书库（bind mount 的 DER），不受影响。

### 3.12 背包接口不返回货币类道具

- 现象：感恩日领到“钻石+230”，但背包前后对比表里钻石一直是 0。
- 根因：type 8 背包接口不返回钻石这类货币；钻石只能在领取响应里确认。
- 预防：验证奖励时，奖励来源（领取响应 JSON/二进制明细）与背包变化分开看。

## 4. 协议逆向要点

### 4.1 会话公共字段

登录链路（两种）：
- 账号+密码：`login()` type 4 → `get_token()` type 6659 → 会话
- 通行证/手机号：Gaia 登录（`dawn.shiyiyx.com`）→ LC_ token → `token_login()` type 6674 → 会话

会话关键字段（从 6659/6674 响应解析）：
- offset 32：**account_id**（u32，如 382377872，即 `gc_382377872` 的数字部分）——大多数请求的第一个 u32
- offset 36~52：**token**（16 字符 ASCII）
- `AGENT_ID = 10000046`（= `ae969800` 小端字节，抓包里恒定的渠道常量）
- `GAME_VER = 602`

请求 body 通用组成（示例）：
- type 8 背包：`<u32 account_id><16s token><4 零>`
- 12476 每日福利：`<u32 account_id><16s token><u32 0><u32 602><u32 10000046>`
- 2608 查询：`<u32 sub><u32 602><u32 act_id><u32 account_id><16s token><u64 0><u32 602><u32 10000046><u32 33>`

### 4.2 已知 msgType 表

| msgType | 用途 | 备注 |
|---|---|---|
| 4 | 大世界账号登录 | 返回 username/md5 |
| 8 | 背包道具列表 | `<account_id><token>`，响应 `count + (id,qty)*n` |
| 15 | 查询（小） | fields = `<u32 account_id>` |
| 6659 | 换取会话 token | 模板在 `data/flow5_template.bin` |
| 6674 | LC_ token 登录 | 模板在 `data/tokenlogin_template.bin`，走 TokenLoginReq.do |
| 12349 | 仓库道具 | |
| 12476 | VIP 每日福利领取 | 响应二进制：result + 0x15 + count + (id,qty) |
| 12477 | VIP 福利列表/状态查询 | 32 字节基础 + u32 参数（1=周期, 4=列表） |
| 2608 | 活动通用（感恩日等） | sub=0 查询 JSON / sub=1 领取 JSON；act_id=1001 为感恩日 VIP尊享福利 |

### 4.3 响应两种格式

- **二进制**（如 12476）：u32 iResult（0=成功）+ 结构化字段，逐偏移解析；
- **JSON**（如 2608）：响应 = JSON + 尾部杂字节（`\0` 等），解析时取 `text[find('{') : rfind('}')+1]`；
- 失败响应：iResult 非 0，后跟 `\0` 结尾的中文提示（`_resp_error_message` 同款解析）。
- 金币（背包/主页面显示值）只在登录响应（6659/6674 offset 128）返回一次，客户端本地维护，不存在免登录查金币接口（2026-08-16 专项抓包实证）；仓库金币可经 0xE3 实时查询（pid 10000）。
