# 安全防护优化文档（待实施）

> 创建日期：2026-08-13
> 状态：**已实施（心跳 + Nuitka 已随 1.0.1 打包）**
> 目标：防止用户端软件泄露到圈子外后被破解长期使用

## 1. 背景与目标

- 用户端 BydsjApp.exe 未来会分发给朋友，存在被转发、被破解的风险；
- 目标是：即使软件流入外人手里，也难以绕过卡密长期使用；
- 管理端 BydsjAdmin.exe 不分发，不在本次防护范围内；
- 本方案只讨论技术手段，不把“不公开分发”作为唯一依赖。

## 2. 威胁模型

- 普通用户：无法绕过卡密激活 → 已被现有机制挡住；
- 懂一点技术的人：反编译 PyInstaller 字节码、patch 启动激活 → **需要心跳校验拦截**；
- 专业逆向者：可 patch 全部客户端校验 → 需要提高逆向成本（Nuitka）；
- 绝对防破解不存在；若追求极致，只能服务端化（已评估，不建议，见第 6 节）。

## 3. 方案一：心跳校验（用户端）

### 机制

- 客户端激活成功后，将卡密保存在内存（用户无需重复输入）；
- 主界面运行期间，后台定时调用服务器 `/api/client/validate`，提交“卡密 + 本机机器码”；
- 服务器核对：卡密存在 / 未过期 / 未停用 / 绑定本机；
- 校验通过 → 继续使用；不通过 → 锁定。

### 默认参数（可调整）

- 校验间隔：30 分钟
- 服务器无响应宽限期：10 分钟（避免误伤）
- 锁定表现：弹窗“卡密已失效/被停用/已过期，请联系管理员”，无法继续操作，回到激活流程或退出

### 说明

- 心跳与“启动激活”是两段独立代码，只 patch 启动激活的人仍会被心跳锁住；
- 若专业逆向者连心跳一起 patch，则本方案失效，需依赖 Nuitka 提高门槛。

## 4. 方案二：用户端换 Nuitka 原生打包

- 现状：PyInstaller 单文件 exe（Python 字节码，易反编译）；
- 目标：改用 Nuitka 编译为原生 exe，显著提高逆向难度；
- 要求：
  - 仍输出单文件 exe，目录结构不变；
  - 协议模板、道具图标、app_icon.ico、updater.exe 全部照常内嵌；
  - 热更新机制不受影响（updater 替换 exe 的流程不变）；
  - 打包脚本更新为 Nuitka 版（可保留 packaging/build.py 作为统一入口）；
  - 需要验证 PySide6 + Nuitka 的打包兼容性。
- 版本策略：
  - 尚未分发 → 新版仍可保持 1.0.0；
  - 若已有人拿到旧版 1.0.0 → 升级为 1.0.1 再发布。

## 5. 可选加固（按需再做）

1. 管理端登录限流：同一 IP 连续失败 5 次锁定 15 分钟；
2. HTTPS / 自签名加密：防止抓包截获未绑定卡密；
3. 卡密导出/管理增加审计日志。

## 6. 明确不做：服务端代理

- 曾评估“把核心价值搬到服务器”（客户端只做显示壳）：
  - 开发量大、服务器成为游戏流量瓶颈；
  - 所有账号从服务器 IP 登录会触发游戏风控；
  - 账号密码需上传服务器，隐私/信任成本高；
  - 短信验证码交互复杂；
- 结论：**不做**，Nuitka + 心跳校验为当前性价比最高的组合。
